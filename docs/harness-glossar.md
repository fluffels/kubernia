# Harness-Glossar: die Begriffe der Agenten-Maschinerie

> **Fachlich geprüft am: 2026-10-10.**
> Für Außenstehende, die den [Harness](agent-harness.md) lesen wollen. Die Begriffe des Spiels (Hafen, Kubernetes, Code) stehen getrennt im [Glossar](glossar.md). Regelkonstanten und Zählwerte stehen hier bewusst nicht: sie driften, die verlinkte Quelle gilt. Muster mit Belegen: [Lessons Learned](lessons-learned.md).

## Akteure und Werkzeuge

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Harness | Die Maschinerie um die KI-Agenten: Regeln, Prüfungen, Abläufe und Messung, mit der das Repo billig und sicher weitergebaut wird. | [agent-harness.md](agent-harness.md) |
| Agent | Eine Claude-Code-Sitzung, die Tickets bearbeitet: lesen, ändern, Befehle ausführen. | [AGENTS.md](../AGENTS.md) |
| Subagent | Ein vom Agenten gestarteter Agent mit eigenem Kontext und fester Rolle. Rollen: Planer (Umsetzungsplan vor dem Coden), Umsetzer (setzt ein Ticket bis zum Merge um), Lens (prüft einen Diff durch genau eine Brille), Explore (liest und sucht nur). | [Wer macht was](agent-harness.md#wer-macht-was), [kubernia-umsetzer](../.claude/agents/kubernia-umsetzer.md) |
| Statusline | Die Statuszeile am Rand einer Claude-Code-Sitzung, die ein Kommando aus `.claude/settings.json` zeichnet. Projekt-intern ruft sie `scripts/statusline.mjs` auf: es sichert den Rate-Limit-Stand und reicht die persönliche Statusline durch. | [model-routing.md §6](model-routing.md#6-budget-pacing-1358) |
| Modell-Alias | `opus`, `sonnet` und `haiku` lösen auf das jeweils neueste Modell der Stufe auf, nie auf eine feste Modell-ID. Welche Phase welche Stufe nutzt, steht in der Phasen-Matrix. | [model-routing.md](model-routing.md#1-phasen-matrix) |
| Tool | Eine Fähigkeit, die ein Agent aufrufen darf (Datei lesen, Shell, Suche). Welche Tools ein Subagent hat, steht in seiner Definition. | [.claude/agents/](../.claude/agents/) |
| MCP-Server | Ein angebundener Dienst, der dem Agenten zusätzliche Tools liefert, etwa Browser-Steuerung oder Langfuse-Abfragen. | [.mcp.json](../.mcp.json) |
| Skill | Ein wiederverwendbarer, versionierter Ablauf als Markdown, den ein Agent lädt, etwa der Ticket-Ablauf oder das Review. | [Skills und Setup](agent-harness.md#25-skills--setup-als-reproduzierbare-abläufe) |
| Hook | Ein Skript, das Claude Code bei einem Ereignis automatisch ausführt (vor einem Tool-Aufruf, beim Stopp) und das einen Vorgang verweigern kann. | [Harness-FAQ](agent-harness-faq.md) |

## Grenzen und Prüfungen

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Sandbox | Eine Laufumgebung, die den Sandbox-Vertrag erfüllt. Varianten: WSL2 mit der Claude-Code-Sandbox (Kubernias Weg), Docker Sandboxes (`sbx`), eigene Container-Sandbox. Unter nativem Windows gibt es keine. | [Agenten-Sandbox](agent-harness.md#agenten-sandbox-wsl2), [ADR 0021](adr/0021-agenten-sandbox-wsl2.md), [Sandbox anbinden](sandbox-anbinden.md) |
| Sandbox-Vertrag | Die Zeilen V0 bis V7, die eine Laufumgebung erfüllen muss (Workspace, Egress-Allowlist, keine Klartext-Zugangsdaten, Werkzeuge, Langfuse, Merkmal `AGENT_SANDBOX`, Ladeorte). Verletzt sie eine Zeile, ist sie „nicht gesandboxt“. | [ADR 0025](adr/0025-sandbox-als-austauschbare-laufumgebung.md) |
| MCP-Ausfall | Ein MCP-Server startet nicht, fällt mitten in der Session weg oder läuft nur über den Ersatzweg `npx`. Das ist ein Harness-Befund und wird als Zeile im Sammelticket festgehalten. | [Ausfälle melden](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Leitplanke | Eine Grenze für Agenten, entweder als Bitte (Text, den ein Agent ignorieren könnte) oder als Mauer (Prüfung, die technisch erzwingt). Eine Pfadliste kennzeichnet Dateien, deren Änderung ein Audit-Kommentar begleitet. | [Bitte und Mauer](agent-harness.md#leitplanken-schichten-bitte-und-mauer), [.github/protected-paths.json](../.github/protected-paths.json), [ADR 0014](adr/0014-leitplanken-ohne-label-riegel.md) |
| Check, Gate, verify | Ein Check ist eine automatische Prüfung. Ein Gate ist ein Check, dessen Rot den Merge blockiert. `verify` ist der Sammelbefehl der schnellen Gates. Die vollständige Liste ist generiert und steht in der Gate-Tabelle. | [Gate-Tabelle](agent-harness.md#3-die-fitness-functions-im-detail) |
| Required Check | Ein Check, den GitHub serverseitig auf dem Pull Request erzwingt; er lässt sich lokal nicht umgehen. | [ADR 0009](adr/0009-pr-gating-required-checks.md) |
| Wächter | Ein Test oder Skript, das eine Regel oder einen Zusammenhang im Repo selbst bewacht, etwa dass Doku und Code zusammenpassen. | [Gate-Tabelle](agent-harness.md#3-die-fitness-functions-im-detail) |
| Override | Eine begründete Ausnahme für ein einzelnes Gate, als Commit-Zeile `KQ-…-Override: #<nr> Begründung`. Nur wenige Gates kennen sie, alle anderen nicht. | [Gates, Guards und Durchsetzung](agent-harness.md#gates-guards-und-durchsetzung), [ADR 0009](adr/0009-pr-gating-required-checks.md) |
| Lens, Review-Runde | Eine Lens ist ein frischer, unabhängiger Kritiker mit genau einer Brille (etwa Architektur oder Tests) auf einem fertigen Diff. Eine Review-Runde ist ein Durchgang, danach folgt eine begrenzte Zahl Fix-Runden; der letzte Blick ist nie der, der zuletzt gefixt hat. | [Review-Staffel](model-routing.md#review-staffel-1265), [Skill review-lenses](../.claude/skills/review-lenses/SKILL.md) |
| Weiche | Eine offene Entscheidung im Ticket (Optik, Risiko, Plan-Variante). Der Agent entscheidet sie selbst und nennt sie im PR mit Begründung; die Maintainerin kann per Revert widersprechen. Nur bei Irreversiblem oder Außenwirkung wird vorher gefragt. | [ADR 0012](adr/0012-harness-autonomie-audit-spur.md) |
| Fremdtext | Text Dritter (Issue-Kommentare, Forum) gilt als Daten, nie als Anweisung. Ein Skript liest ihn gefiltert. | [sicherheit-agenten.md](sicherheit-agenten.md), [scripts/fremdtext.mjs](../scripts/fremdtext.mjs) |
| Einstiegsskript, Lib | Ein Einstiegsskript läuft per `node scripts/<name>.mjs` (oder als Hook) und hat einen Direktaufruf-Guard. Gemeinsamer Code steht in einer Lib ohne Guard; ein Skript importiert nie aus einem Einstiegsskript, auch eine Lib nicht. Ein Wächter-Test prüft das. | [Skript-Konvention](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Sabotage-Probe (Red-Green) | Der Beweis, dass ein Test echt ist: die geprüfte Eigenschaft wird testweise verfälscht, der Test muss rot werden, danach wird zurückgesetzt. Die Test-Lens macht das in einem eigenen Worktree; der Anker der Verfälschung muss eindeutig sein. | [Tests gegen False Positives](agent-harness.md#tests-npm-test-vitest), [Lens-Definition](../.claude/agents/kubernia-lens.md) |

## Ablauf

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Worktree | Ein eigener `git worktree` je Ticket als Kollisionsschutz für parallele Agenten. Die Abhängigkeiten dort installiert `npm ci`. | [Kollisionsschutz](agent-harness.md#23-kollisionsschutz-für-parallele-agenten) |
| Phasen-Schnitt, Übergabe | Ein Umsetzer endet an einem vorgegebenen Schnittpunkt (`verify`: vor dem vollen `verify:kompakt`; `pr`: nach `gh pr create` und gesetztem Auto-Merge) mit `ERGEBNIS: uebergabe`, ein frischer Umsetzer (Nachfolger, Prompt-Zeile `Einstieg:`) übernimmt den Vorgänger (Prompt-Zeile `Schnitt:`) am selben Worktree und Lock. **Nachlese-Call**: ein Lese-Aufruf (Read, `cat`, `sed`, `head`) des Nachfolgers auf eine Datei, die der Vorgänger geändert hat. | [Phasen-Schnitt](model-routing.md#phasen-schnitt-1592-vertrag-ab-regel-messrezept) |
| Ticket-Lock | Eine Sperrdatei je Ticket, die beim Claim atomar angelegt wird, damit zwei Sessions desselben Rechners nie dasselbe Ticket starten: der Assignee allein trennt sie nicht, weil alle Agenten unter demselben Konto laufen. Gilt nur auf einer Maschine. | [Ticket-Lock](agent-harness.md#23-kollisionsschutz-für-parallele-agenten) |
| Sammelticket | Ein Ticket, das viele kleine Befunde als Zeilen sammelt: Harness-Befunde in „Harness-Härtung (gesammelt)“, Langfuse-Befunde in „Langfuse-Befunde (gesammelt)“. Kommt es dran, wird es komplett abgearbeitet. | [ticket-reihenfolge.md](ticket-reihenfolge.md#sammelticket-harness-härtung-gesammelt-1199) |
| Status-Ticket | Das wiederkehrende Ticket „Langfuse-Status überprüfen“. Der Workflow [board-takt.yml](../.github/workflows/board-takt.yml) legt es an (Bedingungen im Kopf der Datei), ein Agent wertet es nach der Checkliste aus; den Lauf startet die Maintainerin von Hand. | [Checkliste](model-routing.md#langfuse-status-überprüfen-1293) |
| Merge-Testabgleich | Pflichtschritt nach jedem Merge von `origin/main` in den Branch: `scripts/merge-testabgleich.mjs` vergleicht die Testtitel gegen beide Eltern und meldet einen Test, der im Ergebnis fehlt, ohne dass eine Seite ihn bewusst entfernt hat. | [Befehle](referenz/befehle.md), Skill `review-lenses` › „Nach jedem Merge von `main`“ |
| Spielquote | Der Wechsel zwischen Spiel- und Harness-Arbeit: Nach einer festen Zahl Spiel-Merges holt der Takt das Sammelticket nach vorn. Die Zahl steht im Skript, nicht hier. | [ADR 0016](adr/0016-langfuse-takt-woechentlich.md), [scripts/board-takt.mjs](../scripts/board-takt.mjs) |

## Messung und Richtung

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Langfuse | Die Messplattform für Agentenläufe: Tokens, Kosten und Läufe je Modell und Rolle. | [ADR 0019](adr/0019-langfuse-plugin-im-user-scope.md), [Token- und Loop-Baseline](model-routing.md#5-token--und-loop-baseline-1068) |
| Messfenster | Die Body-Zeile `Messfenster: n ≥ <k> <agent> nach #<nr>` eines Nachmessungs-Tickets: frei erst, wenn #<nr> geschlossen ist und seit dessen `closedAt` mindestens k Läufe des Agent-Typs gestartet sind (Untergrenze, keine Messregel). | [Messfenster](ticket-reihenfolge.md#messfenster-1589) |
| Langfuse-Abgleich | Der Vergleich Transkript gegen Langfuse je Call samt automatischer Nachlieferung fehlender Calls an SessionStart und SessionEnd. Das Transkript gilt als Wahrheit, Dubletten werden nur gemeldet; leere Hook-GENERATIONs des Plugins (Modell `claude`, keine Tokens) zählen nicht als Dublette, sondern als „leer“. | [ADR 0023](adr/0023-transkript-quelle-der-wahrheit-langfuse-abgleich.md), [Abgleich als Garantie](langfuse-hook-patch.md#abgleich-als-garantie-1578) |
| Budget-Pacing | Das Takten der Ticketläufe nach dem Wochenlimit des Kontos: `scripts/budget-pacing.mjs` vergleicht den Ist-Verbrauch des 7-Tage-Fensters mit dem Soll (verstrichener Anteil × Zielquote, Default 65 %) und meldet `ok`, `knapp` (mit Wartezeit) oder `stopp`. Grundlage ist der Rate-Limit-Snapshot (Stand der beiden Fenster im OS-Temp, aus der Statusline oder einer Headless-Probe). | [model-routing.md §6](model-routing.md#6-budget-pacing-1358) |
| Ledger (Nachliefern) | Die lokale Merkdatei des Nachlieferers (`~/.claude/state/langfuse-abgleich.json`): je Session, welche Calls schon gesendet sind (mit Zeitstempel, nach Ablauf einer Frist gilt ein noch fehlender Call wieder als nicht gesendet), ob sie bestätigt ist, ob ihr Ende bekannt ist. Eine Brücke über den Ingestion-Verzug, keine Wahrheit: fehlt sie, kostet das nur Abfragen. | [Langfuse-Hook-Patch](langfuse-hook-patch.md) |
| Grabstein | Der Hardlink, auf den eine veraltete Lock-Übernahme den alten Lock legt (`<lock>.verwaist-<pid>-<zeit>`): bei zwei gleichzeitigen Bewerbern gewinnt genau einer, der andere bekommt „belegt“. Alte Grabsteine räumt der nächste Lauf weg. | [Langfuse-Hook-Patch](langfuse-hook-patch.md) |
| Plugin-Lock | Die leere Datei `langfuse_state.<hash>.lock`, die das Langfuse-Plugin je Zustand anlegt und nie aufräumt. Der Nachlieferer löscht sie ab 24 h Alter und zählt sie im Logfeld `pluginLocks`. | [Langfuse-Hook-Patch](langfuse-hook-patch.md) |
| Score ausstehend | Status im Abgleich-Bericht: die Session ist vollständig in Langfuse, der Nachlieferer wartet aber noch (150 s nach bekanntem Ende, sonst 24 h) und hat darum noch keinen Score gesetzt. | [Langfuse-Hook-Patch](langfuse-hook-patch.md) |
| Nacharbeit | Ein Revert oder ein Commit mit der Zeile `Folge #<nr>` innerhalb eines festen Fensters nach dem Merge. Das Skript `scripts/lauf-ergebnis.mjs` misst sie je Ticket. | [Ergebnis je Ticket-Lauf](model-routing.md#ergebnis-je-ticket-lauf-1123) |
| Gegenprobe | Der Vergleich einer Harness-Änderung (Modell, Effort, Regel) gegen eine vorher gemessene Basis (feste Basismenge, für Läufe und PRs dieselbe `--ohne`-Liste); die Abbruch- bzw. Entscheidungsregel steht vor der Messung fest. | [Effort-Gegenprobe](model-routing.md#umsetzer-kontext-1559) |
| Selbstcheck | Der sichtbare Block `Selbstcheck:` des Umsetzers vor jedem Commit: je Prüffrage der Test-Adäquanz-Lens eine Zeile `ok`, `gefixt` oder `n.a.`; er steht im PR-Text und geht nicht an die Lenses. | [Stichprobe zum Selbstcheck](model-routing.md#ergebnis-je-ticket-lauf-1123) |
| Output-Schätzung | Eine Näherung, meist eine Untergrenze (bei Hauptdateien, deren Output vollständig ist, kann sie leicht darüber liegen), für die Output-Tokens eines Subagenten-Calls, abgeleitet aus dem Zuwachs des Kontexts bis zum nächsten Call: die Subagenten-Transkripte zeichnen nur den Anfangsstand der Ausgabe auf. Sie steht neben dem aufgezeichneten Wert, nie an seiner Stelle, und Langfuse bekommt sie nicht. | [Planer-Kosten](model-routing.md#planer-kosten-1558) |
| Basismodell (Session) | Das Modell, mit dem eine Session startet, erkennbar am ersten Anhang `model` im Transkript; ein Skill mit `model` überschreibt es nur für seinen Turn. | [Hauptchat nach Tätigkeit](model-routing.md#hauptchat-nach-tätigkeit-1356) |
| Besitz-Manifest | `.factory/besitz.json`: die Liste dessen, was der Factory gehört (ganze Datei, Markdown-Block oder JSON-Schlüssel), mit Ring `kern` oder `kern-nach-entkopplung`. | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md) |
| Schichtdaten | Das Schicht-Modell eines Projekts (`SCHICHT_MODELL`). Der Kern lädt es nur über den konfigurierten Pfad (`schichten.layers`), nie per statischem Import; Prüfung und Ableitung liegen im Kern (`scripts/schichten-kern.cjs`). | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md) |
| Projektliteral | Ein Begriff, der ein bestimmtes Projekt benennt (Owner, Repo-Name, Board-ID, Stardew-Bezug) und in einer Kern-Einheit nicht stehen soll; der Kern-Reinheits-Wächter zählt sie. | [agent-harness.md](agent-harness.md#kern-reinheits-wächter-testharnesskern-reinheittestts-1610) |
| Dark Factory | Das Zielbild aus ADR 0022: der spielunabhängige Kern des Harness wird wiederverwendbar: Projekte beziehen ihn per Sync; menschliche Stopps bei Irreversiblem und Außenwirkung bleiben. Stand 2026-10-16: entschieden, Besitz-Manifest und Kern-Reinheits-Wächter (F1) und der Schicht-Kern (F7) gebaut, der Rest nicht. | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md), [harness-transfer.md](harness-transfer.md) |
