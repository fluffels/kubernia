# Harness-Glossar: die Begriffe der Agenten-Maschinerie

> **Fachlich geprüft am: 2026-10-10.**
> Für Außenstehende, die den [Harness](agent-harness.md) lesen wollen. Die Begriffe des Spiels (Hafen, Kubernetes, Code) stehen getrennt im [Glossar](glossar.md). Regelkonstanten und Zählwerte stehen hier bewusst nicht: sie driften, die verlinkte Quelle gilt. Muster mit Belegen: [Lessons Learned](lessons-learned.md).

## Akteure und Werkzeuge

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Harness | Die Maschinerie um die KI-Agenten: Regeln, Prüfungen, Abläufe und Messung, mit der das Repo billig und sicher weitergebaut wird. | [agent-harness.md](agent-harness.md) |
| Agent | Eine Claude-Code-Sitzung, die Tickets bearbeitet: lesen, ändern, Befehle ausführen. | [AGENTS.md](../AGENTS.md) |
| Hauptchat | Die Claude-Code-Sitzung der Maintainerin: nimmt Aufträge an, wählt das Ticket und startet die Subagenten. Alle Rollen aus „Subagent“ laufen unter ihm. | [AGENTS.md](../AGENTS.md) |
| Subagent | Ein vom Agenten gestarteter Agent mit eigenem Kontext und fester Rolle. Rollen: Planer (Umsetzungsplan vor dem Coden), Umsetzer (setzt ein Ticket bis zum Merge um), Gruppen-Umsetzer (setzt eine Gruppe von Sammelticket-Zeilen um), Lens (prüft einen Diff durch genau eine Brille), Explore (liest und sucht nur). | [Wer macht was](agent-harness.md#wer-macht-was), [kubernia-umsetzer](../.claude/agents/kubernia-umsetzer.md) |
| Zwischen-Hand-off | Ein Bericht des Umsetzers, der kein Ende ist (kein gültiges Token, Zusatz wie „Zwischenstand“, offener PR mit Auto-Merge oder keine Zeile `BEFUNDE:`); der Hauptchat setzt denselben Umsetzer fort statt zu berichten. | [Skill kubernia](../.claude/skills/kubernia/SKILL.md) |
| Fortsetzungsauftrag | Ein Auftrag wie „mach mit <nr> weiter“ oder „weiter“, oft ohne den Skill `kubernia`. Er läuft wie ein Ticketlauf: der Hauptchat liest den Zustand (Worktree, PR, KQ-Zeilen, Lock), der Planer plant die Restarbeit, ein Umsetzer übernimmt den vorhandenen Worktree. Die Abschluss-Pflichten (Befunde eintragen, `brain-input`) gelten auch dort. | [Am Ticket-Ende](ticket-reihenfolge.md#am-ticket-ende) |
| Statusline | Die Statuszeile am Rand einer Claude-Code-Sitzung, die ein Kommando aus `.claude/settings.json` zeichnet. Projekt-intern ruft sie `scripts/statusline.mjs` auf: es sichert den Rate-Limit-Stand und reicht die persönliche Statusline durch. | [model-routing.md §6](model-routing.md#6-budget-pacing-1358) |
| Modell-Alias | `opus`, `sonnet` und `haiku` lösen auf das jeweils neueste Modell der Stufe auf, nie auf eine feste Modell-ID. Welche Phase welche Stufe nutzt, steht in der Phasen-Matrix. | [model-routing.md](model-routing.md#1-phasen-matrix) |
| Tool | Eine Fähigkeit, die ein Agent aufrufen darf (Datei lesen, Shell, Suche). Welche Tools ein Subagent hat, steht in seiner Definition. | [.claude/agents/](../.claude/agents/) |
| MCP-Server | Ein angebundener Dienst, der dem Agenten zusätzliche Tools liefert, etwa Browser-Steuerung oder Langfuse-Abfragen. | [.mcp.json](../.mcp.json) |
| MCP-Launcher | Ein Startskript unter `scripts/`, das einen lokalen MCP-Server mit der Version aus dem Lockfile startet: lokal bei passender Version, sonst `npx -y <paket>@<exakte Version>`, nie ungepinnt. Die gemeinsame Logik steckt in `scripts/mcp-launch.mjs`, je Server ein dünner Wrapper (`playwright-mcp.mjs`, `likec4-mcp.mjs`). | [mcp-launch.mjs](../scripts/mcp-launch.mjs) |
| Architekturmodell | Das LikeC4-Modell unter `docs/architektur/` (Spiel-App, Harness, Beziehungen). `check:c4` gleicht es mit dem Repo ab, Agenten fragen es über den LikeC4-MCP ab; der MCP ist nie Gate-Quelle. | [ADR 0020](adr/0020-architekturmodell-likec4.md), [FAQ](agent-harness-faq.md#wie-frage-ich-das-architekturmodell-ab) |
| Skill | Ein wiederverwendbarer, versionierter Ablauf als Markdown, den ein Agent lädt, etwa der Ticket-Ablauf oder das Review. | [Skills und Setup](agent-harness.md#25-skills--setup-als-reproduzierbare-abläufe) |
| Workflow | Ein Ablauf-Skript unter `.claude/workflows/`, das die Phasen eines Tickets selbst startet (im Unterschied zum Skill, den ein Agent liest). | derzeit keiner; der Ticket-Ablauf ist der Skill-Pfad ([ADR 0028](adr/0028-ein-ticket-ablauf.md)) |
| Skill-Pfad | Der Ticket-Ablauf über den Skill im Hauptchat mit Umsetzer-Subagent: der einzige Ticket-Ablauf ([ADR 0028](adr/0028-ein-ticket-ablauf.md)). | [ADR 0026](adr/0026-sammelticket-gruppen.md) |
| Hook | Ein Skript, das Claude Code bei einem Ereignis automatisch ausführt (vor einem Tool-Aufruf, beim Stopp) und das einen Vorgang verweigern kann. | [Harness-FAQ](agent-harness-faq.md) |

## Grenzen und Prüfungen

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Sandbox | Eine Laufumgebung, die den Sandbox-Vertrag erfüllt. Varianten: WSL2 mit der Claude-Code-Sandbox (Kubernias Weg), Docker Sandboxes (`sbx`), eigene Container-Sandbox. Unter nativem Windows gibt es keine. | [Agenten-Sandbox](agent-harness.md#agenten-sandbox-wsl2), [ADR 0021](adr/0021-agenten-sandbox-wsl2.md), [Sandbox anbinden](sandbox-anbinden.md) |
| Sandbox-Vertrag | Die Zeilen V0 bis V7, die eine Laufumgebung erfüllen muss (Workspace, Egress-Allowlist, keine Klartext-Zugangsdaten, Werkzeuge, Langfuse, Merkmal `AGENT_SANDBOX`, Ladeorte). Verletzt sie eine Zeile, ist sie „nicht gesandboxt“. | [ADR 0025](adr/0025-sandbox-als-austauschbare-laufumgebung.md) |
| SBOM | Stückliste der npm-Abhängigkeiten im Format CycloneDX, je CI-Build als Artefakt (`npm run sbom`). Die SBOM des Release-Images ist SPDX. | [Befehle](referenz/befehle.md) |
| MCP-Ausfall | Ein MCP-Server startet nicht, fällt mitten in der Session weg oder läuft nur über den Ersatzweg `npx`. Das ist ein Harness-Befund und wird als Zeile im Sammelticket festgehalten. | [Ausfälle melden](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Leitplanke | Eine Grenze für Agenten, entweder als Bitte (Text, den ein Agent ignorieren könnte) oder als Mauer (Prüfung, die technisch erzwingt). Eine Pfadliste kennzeichnet Dateien, deren Änderung ein Audit-Kommentar begleitet. | [Bitte und Mauer](agent-harness.md#leitplanken-schichten-bitte-und-mauer), [.github/protected-paths.json](../.github/protected-paths.json), [ADR 0014](adr/0014-leitplanken-ohne-label-riegel.md) |
| Pflicht-View | Eine View des Architekturmodells, die laut `architektur.pflichtViews` im Modell stehen muss (mindestens der Ticket-Lauf). | [Architekturmodell-Wächter](agent-harness.md#architekturmodell-wächter-npm-run-checkc4-1420), [ADR 0020](adr/0020-architekturmodell-likec4.md) |
| Check, Gate, verify | Ein Check ist eine automatische Prüfung. Ein Gate ist ein Check, dessen Rot den Merge blockiert. `verify` ist der Sammelbefehl der schnellen Gates. Die vollständige Liste ist generiert und steht in der Gate-Tabelle. | [Gate-Tabelle](agent-harness.md#3-die-fitness-functions-im-detail) |
| Check-Kategorie | Die Einteilung der CI-Checks eines PR für `scripts/pr-warten.mjs`: ein **Pflicht-Check** (laut `gh pr checks --required` ein Required Check) gatet, sein Rot ist `ROT`; jeder andere Check, etwa CodeQL oder die Deploy-Validierung, sperrt den Merge nicht, sein Rot ist nur ein `HINWEIS`. Lässt sich die Pflicht-Liste nicht holen oder ist sie leer, gatet jeder Check (fail-closed). | [Code-Scanning und Posture](agent-harness.md#code-scanning-und-posture-codeqlyml-scorecardyml-875) |
| Required Check | Ein Check, den GitHub serverseitig auf dem Pull Request erzwingt; er lässt sich lokal nicht umgehen. | [ADR 0009](adr/0009-pr-gating-required-checks.md) |
| Spezifikations-Gate | Die Eingangsprüfung der Ticket-Auswahl: ein Ticket braucht `## Ziel` und `## Akzeptanzkriterien` mit mindestens einem Negativfall, sonst wird es übersprungen, gemeldet und über den [Reparaturweg](ticket-reihenfolge.md#reparaturweg-1698) nachgezogen (Bestand wird nur berichtet). | [Spezifikations-Gate](ticket-reihenfolge.md#spezifikations-gate-1615), [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md) |
| Reparaturweg | Der Weg, ein vertrautes Ticket ohne Spezifikation nachzuziehen: die Auswahl meldet `reparieren #<nr>`, der Agent leitet Ziel und Akzeptanzkriterien aus dem vorhandenen Text ab, `spezifikation.mjs reparieren` schreibt nur ohne Inhaltsverlust und nie bei einem Fremdeingang. | [Reparaturweg](ticket-reihenfolge.md#reparaturweg-1698), [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md) |
| Wächter | Ein Test oder Skript, das eine Regel oder einen Zusammenhang im Repo selbst bewacht, etwa dass Doku und Code zusammenpassen. | [Gate-Tabelle](agent-harness.md#3-die-fitness-functions-im-detail) |
| Override | Eine begründete Ausnahme für ein einzelnes Gate, als Commit-Zeile `<Präfix>…-Override: #<nr> Begründung`; das Präfix kommt aus `praefixe.commitZeile` der Projekt-Config (hier `KQ-`). Nur wenige Gates kennen sie, alle anderen nicht. Ein weiterer leerer Commit mit der Zeile `<Präfix>…-Override: #<nr> entfällt` nimmt sie zurück (Widerruf). | [Gates, Guards und Durchsetzung](agent-harness.md#gates-guards-und-durchsetzung), [ADR 0009](adr/0009-pr-gating-required-checks.md) |
| Lens, Review-Runde | Eine Lens ist ein frischer, unabhängiger Kritiker mit genau einer Brille (etwa Architektur oder Tests) auf einem fertigen Diff. Eine Review-Runde ist ein Pass, danach folgt eine begrenzte Zahl Fix-Runden; der letzte Blick ist nie der, der zuletzt gefixt hat. | [Review-Staffel](model-routing.md#review-staffel-1265), [Skill review-lenses](../.claude/skills/review-lenses/SKILL.md) |
| Zusatzpass | Ein Review-Pass nach den zwei Fix-Runden (dem Cap). Den ersten fährt der Umsetzer ohne Rückfrage, die Ursache steht im PR-Text und im Nachweis (`zusatzpass=1:<ursache>`); jeden weiteren gibt nur die Maintainerin frei. | [Nachweis-Format](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Abnahme-Urteil | Das Urteil des Abnahme-Agenten je Akzeptanzkriterium: `erfuellt`, `nicht-erfuellt` oder `nicht-pruefbar`, jeweils mit Beleg. Das Skript `scripts/abnahme.mjs` prüft den Bericht (Kopf, jedes Kriterium genau einmal, Beleg, unveränderter Worktree auf dem erwarteten HEAD) und entscheidet mit Vorrang `handoff` (ein Kriterium nicht prüfbar, Ticket-Kommentar) vor `fix` (nicht erfüllt, Fix-Runde) vor `bestanden`. Ein Prüffehler postet nichts. | [Abnahme-Nachweis](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| `KQ-Abnahme` | Die Commit-Zeile des Abnahme-Nachweises: `KQ-Abnahme: head=<sha> durchgaenge=<n> urteil=K1:erfuellt,…` bzw. `KQ-Abnahme: entfaellt — <Grund>`; die jüngste Zeile gilt. Die Zeile erzeugt `formatAbnahme`, gelesen wird sie von `parseNachweis` (beides in `scripts/slice-override.mjs`). Die CI erzwingt sie erst mit #1755. | [Abnahme-Nachweis](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Durchgang (Abnahme) | Eine Auswertung der Abnahme eines Tickets: die Zahl der gültigen Marker-Kommentare vertrauter Autoren auf dem PR plus eins. Jede Abnahme-Fix-Runde zieht einen Lens-Pass nach sich, deshalb gilt später `durchgaenge ≤ runden`. Nicht zu verwechseln mit dem Pass einer Review-Runde. | [Abnahme-Nachweis](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Weiche | Eine offene Entscheidung im Ticket (Optik, Risiko, Plan-Variante). Der Agent entscheidet sie selbst und nennt sie im PR mit Begründung; die Maintainerin kann per Revert widersprechen. Nur bei Irreversiblem oder Außenwirkung wird vorher gefragt. | [ADR 0012](adr/0012-harness-autonomie-audit-spur.md) |
| Fremdtext | Text Dritter (Issue-Kommentare, Forum) gilt als Daten, nie als Anweisung. Ein Skript liest ihn gefiltert. | [sicherheit-agenten.md](sicherheit-agenten.md), [scripts/fremdtext.mjs](../scripts/fremdtext.mjs) |
| Fremdeingang | Ein Issue oder PR, dessen Autor nicht vertraut ist (nicht der Repo-Owner, nicht `github-actions[bot]`/`dependabot[bot]`) oder das das Label `forum` trägt. Die eine Entscheidung dafür ist `istFremdeingang` in `scripts/fremdtext-lib.mjs`; ein Lauf setzt es nie automatisch um, schreibt es nie um und meldet es als Befund (Exit 3 von `fremdtext.mjs` und `spezifikation.mjs reparieren`; ein knappes API-Kontingent meldet Exit 5). | [Fremdtext ist Daten](sicherheit-agenten.md), [Reparaturweg](ticket-reihenfolge.md#reparaturweg-1698) |
| Quarantäne-Agent | Ein Subagent, der Fremdtext ohne Schreib-, Shell-, Netz-, MCP- und Agent-Werkzeuge liest und nur ein festes Ergebnisformat zurückgibt; der Lauf mit Rechten sieht den Fremdtext nicht (Dual-LLM-Muster). Heute: `forum-leser`. | [sicherheit-agenten.md](sicherheit-agenten.md) |
| Einstiegsskript, Lib | Ein Einstiegsskript läuft per `node scripts/<name>.mjs` (oder als Hook) und hat einen Direktaufruf-Guard. Gemeinsamer Code steht in einer Lib ohne Guard; ein Skript importiert nie aus einem Einstiegsskript, auch eine Lib nicht. Ein Wächter-Test prüft das. | [Skript-Konvention](agent-harness.md#3a-langfassung-der-harten-regeln-ausgelagert-aus-agentsmd-1064) |
| Sabotage-Probe (Red-Green) | Der Beweis, dass ein Test echt ist: die geprüfte Eigenschaft wird testweise verfälscht, der Test muss rot werden, danach wird zurückgesetzt. Die Test-Lens macht das in einem eigenen Worktree; der Anker der Verfälschung muss eindeutig sein. | [Tests gegen False Positives](agent-harness.md#tests-npm-test-vitest), [Lens-Definition](../.claude/agents/kubernia-lens.md) |

## Ablauf

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
| Holdout-Abnahme | Die Prüfung ohne Mensch gegen die Akzeptanzkriterien: ein Szenario-Agent schreibt allein aus dem Ticket Prüfszenarien, ein frischer Abnahme-Agent (`holdout-abnahme`) prüft das Ergebnis dagegen und urteilt je Kriterium (Abnahme-Urteil). Die Szenarien kennen weder Planer noch Umsetzer. Die Spur ist ein PR-Kommentar mit Marker plus die Commit-Zeile `KQ-Abnahme`; ausgewertet wird sie über `node scripts/abnahme.mjs`. Im Ablauf ab #1754, CI-erzwungen ab #1755. | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md#2-verifikation-ohne-mensch-holdout) |
| Board | Ein GitHub-Project-Board der Tickets: die Reihenfolge ist die Position im Board, nicht ein Label. Das oberste freie Item ist das nächste Ticket. Die Config führt eine Liste `boards` mit je einer Rolle. | [ticket-reihenfolge.md](ticket-reihenfolge.md) |
| Produkt-Board | Das Board mit der Rolle `produkt` („Kubernia Backlog“): Spiel- und Inhalts-Tickets. Auswahl, `board-place` und `board-takt` lesen es zusammen mit dem Factory-Board und ordnen Items nach der Trennregel zu. | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md#fortschreibung-1728-2026-10-16-board-liste-und-factory-board-f11-teil-1) |
| Factory-Board | Das Board mit der Rolle `factory` („Factory Backlog“): Harness-Arbeit (Label `area:harness`). Es existiert seit F11 Teil 1; Status-Ticket, Sammeltickets, Harness-Takt und alle offenen Harness-Items stehen auf ihm (Umzug, F11 Teil 3). | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md#fortschreibung-1728-2026-10-16-board-liste-und-factory-board-f11-teil-1) |
| Trennregel | Welches Board ein Issue trägt: genau das Label `area:harness` ergibt das Factory-Board, alles andere das Produkt-Board (`boardRolleFuer` in `scripts/board-lib.mjs`). | [ADR 0022](adr/0022-dark-factory-kern-und-verteilung.md#fortschreibung-1728-2026-10-16-board-liste-und-factory-board-f11-teil-1) |
| Umzug (Board) | `board-place --umzug`: offene Items, die gegen die Trennregel auf dem falschen Board stehen, ans Ende des richtigen Boards setzen und vom falschen entfernen; idempotent, mit `--dry-run`. | [ticket-reihenfolge.md](ticket-reihenfolge.md#spielquote-über-zwei-boards-1729) |
| Worktree | Ein eigener `git worktree` je Ticket als Kollisionsschutz für parallele Agenten. Die Abhängigkeiten dort installiert `npm ci`. | [Kollisionsschutz](agent-harness.md#23-kollisionsschutz-für-parallele-agenten) |
| Phasen-Schnitt, Übergabe | Ein Umsetzer endet an einem vorgegebenen Schnittpunkt (`verify`: vor dem vollen `verify:kompakt`; `pr`: nach `gh pr create` und gesetztem Auto-Merge) mit `ERGEBNIS: uebergabe`, ein frischer Umsetzer (Nachfolger, Prompt-Zeile `Einstieg:`) übernimmt den Vorgänger (Prompt-Zeile `Schnitt:`) am selben Worktree und Lock. **Nachlese-Call**: ein Lese-Aufruf (Read, `cat`, `sed`, `head`) des Nachfolgers auf eine Datei, die der Vorgänger geändert hat. Ein `TaskStop` des eigenen Umsetzers ist kein Schnitt: `ticket-lock.mjs gestoppt` macht den Worktree übernehmbar, die eine Übergabe je Lock bleibt. | [Phasen-Schnitt](model-routing.md#phasen-schnitt-1592-vertrag-ab-regel-messrezept) |
| Ticket-Lock | Eine Sperrdatei je Ticket, die beim Claim atomar angelegt wird, damit zwei Sessions desselben Rechners nie dasselbe Ticket starten: der Assignee allein trennt sie nicht, weil alle Agenten unter demselben Konto laufen. Gilt nur auf einer Maschine. | [Ticket-Lock](agent-harness.md#23-kollisionsschutz-für-parallele-agenten) |
| Gruppen-Umsetzer | Der Subagent `kubernia-gruppe`: setzt im Worktree des Umsetzers eine Gruppe von Zeilen eines Sammeltickets um (frischer Kontext, nur Commits und Bericht, kein Push, kein PR). Der Umsetzer startet ihn je Gruppe des Planers (Block `GRUPPEN`) nacheinander und fährt danach verify, Review, PR und Merge. | [ADR 0026](adr/0026-sammelticket-gruppen.md), [kubernia-gruppe](../.claude/agents/kubernia-gruppe.md) |
| Sammelticket | Ein Ticket, das viele kleine Befunde als Zeilen sammelt: Harness-Befunde in „Harness-Härtung (gesammelt)“, Langfuse-Befunde in „Langfuse-Befunde (gesammelt)“. Kommt es dran, wird es komplett abgearbeitet. Es hat keine Zeilengrenze; es gibt höchstens ein ungeclaimtes, beim Claim entsteht der Nachfolger. | [ticket-reihenfolge.md](ticket-reihenfolge.md#sammelticket-harness-härtung-gesammelt-1199) |
| Audit-Einordnung | Die tägliche Einordnung neuer Advisories aus vollem `npm audit` und offenen Dependabot-Alerts (Dedupe über die GHSA-ID): Normalfall eine Zeile im Harness-Sammelticket, Alarm-Ticket `🔒 Security:` nur bei critical, ausgelieferter Produktiv-Abhängigkeit. | [Audit-Einordnung](ticket-reihenfolge.md#audit-einordnung-1628) |
| Code-Scanning-Inbox | Die wöchentliche Einordnung offener Code-Scanning-Alerts (CodeQL, Scorecard): CodeQL high/critical als ein Ticket `🔒 Security: Code-Scanning-Befunde auflösen` an der Board-Spitze, sonst eine Zeile je Regel im Harness-Sammelticket. Funde in Testpfaden (`test/`) werden nie Spitzen-Ticket, sondern Zeile; eine Wiedervorlage `codescanning-<slug>` hält nur Zeilen-Alerts still. | [Code-Scanning-Inbox](ticket-reihenfolge.md#code-scanning-inbox-1436) |
| Wiedervorlage | Ein Prüfpunkt mit Fälligkeitsdatum in `.github/wiedervorlagen.json`. Der tägliche Workflow legt dazu ein Ticket „⏰ Wiedervorlage: …“ ganz oben im Board an; der Agent löscht den Eintrag und schließt das Ticket im selben PR. Das optionale Feld `alerts` (Alert-Nummern, nur bei `codescanning-*`) hält gezielt Spitzen-Alerts in der Code-Scanning-Inbox still. | [Wiedervorlage](ticket-reihenfolge.md#wiedervorlage-1628) |
| Status-Ticket | Das wiederkehrende Ticket „Langfuse-Status überprüfen“. Der Workflow [board-takt.yml](../.github/workflows/board-takt.yml) legt es an (Bedingungen im Kopf der Datei), ein Agent wertet es nach der Checkliste aus; den Lauf startet die Maintainerin von Hand. | [Checkliste](model-routing.md#langfuse-status-überprüfen-1293) |
| Merge-Testabgleich | Pflichtschritt nach jedem Merge von `origin/main` in den Branch: `scripts/merge-testabgleich.mjs` vergleicht die Testtitel gegen beide Eltern und meldet einen Test, der im Ergebnis fehlt, ohne dass eine Seite ihn bewusst entfernt hat. | [Befehle](referenz/befehle.md), Skill `review-lenses` › „Nach jedem Merge von `main`“ |
| Spielquote | Der Wechsel zwischen Produkt- und Factory-Arbeit über beide Boards: Nach einer festen Zahl Produkt-Merges seit dem letzten Factory-Merge wählt die Auswahl die Factory-Seite, sonst die Produkt-Seite (leere Seite: Rückfall auf die andere; ein geclaimtes offenes Nicht-Kopf-Factory-Item, „Factory in Arbeit“, lenkt auf Produkt), und der Takt holt das Sammelticket nach vorn. Die Zahl steht im Skript, nicht hier. | [ADR 0016](adr/0016-langfuse-takt-woechentlich.md), [scripts/spielquote-lib.mjs](../scripts/spielquote-lib.mjs) |
| Kopf (Board) | Die Items ganz oben auf einem Board, die vor der Quote gelten: Notfälle, Dependabot, Forum, Wiedervorlage und das Status-Ticket (Titelmarker, `istKopfItem` in `scripts/board-lib.mjs`). Die Auswahl nimmt die Kopf-Items beider Boards zuerst, nach Rang. | [ticket-reihenfolge.md](ticket-reihenfolge.md#spielquote-über-zwei-boards-1729) |
| Factory-Merge, Produkt-Merge | Ein Commit auf `main`, dessen Titel ein `area:harness`-Issue referenziert (`istHarnessCommit`), ist ein Factory-Merge, jeder andere Ticket-Merge ein Produkt-Merge; Bot-Commits zählen nicht. | [scripts/spielquote-lib.mjs](../scripts/spielquote-lib.mjs) |

## Messung und Richtung

| Begriff | Bedeutung | Mehr dazu |
|---|---|---|
